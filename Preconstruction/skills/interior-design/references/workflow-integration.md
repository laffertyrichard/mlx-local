# Design handoff to local modeling and takeoff

The design skill owns intent and usable alternatives. It does not configure services, authorize execution or measure final quantities.

## Local project anchors

In the original authoring environment, `${OPTIONAL_BLENDER_WORKSPACE}` contains project instructions and `.prime/agent/skills/blender/SKILL.md` plus `.prime/agent/skills/blender-architecture/SKILL.md`. This was verified by reading files on 2026-10-14, without connecting to Blender. It is a project anchor, not a universal dependency or proof of current runtime readiness. In another checkout, locate its applicable instructions and skill versions; do not assume a historical delivery filename is current.

Use those skills when available for live scene operations, source registration, candidate ownership, IFC semantics and saved-file readback. Check the requested task's actual authorization; a design brief does not grant installs, global MCP changes, generated code execution or permission to overwrite a live scene. Keep unrelated modeling work protected. When execution is authorized, use the established isolated candidate workflow and one live writer.

## Portable handoff record

Link these fields to existing project records rather than inventing parallel authorities:

| Field | Purpose |
|---|---|
| Source/view/revision and source ID | Evidence and cross-view relationship |
| Stable room/object/decision ID | Same physical owner through plans, views and revisions |
| Status | Existing retained, removal, proposed option or unresolved |
| Dimension, units, datum and basis | Measured/written/calculated/scaled/inferred; uncertainty preserved |
| Three envelopes and tested operations | Installed footprint, operation and user access, including simultaneous use |
| Selection/SKU status and assembly interfaces | Approved intent versus unresolved exact product/installation |
| Q-ID, impact, owner and provisional treatment | Dependency that must survive model and estimate handoff |
| Maturity/approval scope | Concept versus accepted design versus field/fabrication verification |

When only a concept is requested, provide a concise record/annotated sketch, not a mandatory model package. Geometry shared across plan/section/elevation must use consistent dimensions and datums. Label imagery departures. Check occupied conditions and model against source, not just against its own compiler inputs. File/readback correctness and human/source/design acceptance are separate results.

## Takeoff boundary

Use `plan-area-takeoff` if available for its source/question/callout registers, authoritative measurement manifest and quantity workflow. That skill was read in the originating task's cloud catalog; it is not assumed globally installed here. Reuse its existing IDs and registered scope. If unavailable, deliver the design scope and measurement questions for later takeoff, stating the capability gap.

Keep measured installed quantities separate from concept allowances, waste and order rounding. Unknown quantity is not zero, exclusion or approved addition; do not extract fabrication/purchase quantities from provisional geometry. Record changes to finishes/configuration even when quantities do not change. Handoff related removal, access/protection, connection and restoration questions without inventing technical assemblies or measured amounts.
